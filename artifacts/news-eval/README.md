# Проверочная выборка новостного Pulse — задача B

**разметка — ПРЕДВАРИТЕЛЬНАЯ АГЕНТСКАЯ, не человеческий эталон**.

Независимая разметка по текстам базы, подготовленная 24 сентября 2026 года до настройки правил в этой задаче. Прочитаны AGENTS.md, продуктовый ориентир и весь `docs/plans/news-first-pulse-agent-prompt.md`. Код продукта, текущие классификаторы и модельные ответы не использовались. Сетевых и LLM-вызовов не было. Состояние работы параллельных сессий этим не удостоверяется.

Проверочные ответы не меняются ради улучшения результата. Примеры для настройки должны храниться отдельно в `artifacts/news-tune/`; в этой задаче они не создавались. Нельзя использовать `sample.py`, тексты, метки, причины или пары этой выборки для конструирования правил. Если обнаружена ошибка разметки, её следует зарегистрировать отдельно с причиной и версией, сохранив исходную замороженную выборку и результаты на ней.

## Исходные данные и воспроизведение

База `astrafeed.db` открывалась исключительно URI `file:…/astrafeed.db?mode=ro` с `uri=True`. Контрольный MD5 до и после: `8618099125a806df376354286ccd982e`, совпадает с `artifacts/pulse-slices.json`. Запись, миграции и PRAGMA, меняющие базу, не выполнялись.

Из корня репозитория:

```sh
python3 artifacts/news-eval/sample.py
python3 artifacts/news-eval/sample.py --export /tmp/news-eval-reproduction
```

Первая команда проверяет SHA-256 всех замороженных файлов, повторно извлекает данные и сверяет пять файлов данных побайтно по UTF-8 тексту, проверяет MD5 базы до/после и печатает состав. Вторая создаёт пять файлов данных в **новом, ещё не существующем** каталоге. `--db /абсолютный/путь/astrafeed.db` позволяет явно указать базу. Скрипт использует только stdlib и не импортирует продуктовый код.

`manifest.json` содержит SHA-256 `posts.jsonl`, `comments.jsonl`, `pairs.jsonl`, `windows.json`, `holdout.json`, этого README и `sample.py`. Сам manifest исключён из собственного списка: самоссылочный SHA-256 невозможен. Для независимого контроля SHA-256 manifest приведён в итоговом сообщении задачи; файл manifest не является криптографической подписью.

## Как выбирались примеры

Выборка целевая, с трудными положительными и отрицательными случаями; это не случайная оценка частот во всём потоке. В базе 13 985 публикаций и 1 689 комментариев. Сначала были прочитаны схема SQLite и диапазон времени. Кандидаты извлекались через `SELECT * FROM raw_item`, затем выполнялся поиск в декодированном тексте `\b(zec|zcash|ethereum|eth)\b`, а также по фразам об обновлении, кошельках и доле BitMine. Просматривались короткие анонсы и полные выбранные тексты. Группировка по точному тексту использовалась только для поиска кандидатов-копий. Решения о событиях и связях комментариев принимались при чтении, не автоматически по тикеру.

Финальный воспроизводимый SQL в `sample.py`:

```sql
SELECT * FROM raw_item WHERE id=?;
SELECT count(*) FROM comment WHERE source_id=? AND post_id=?;
SELECT * FROM comment WHERE source_id=? AND post_id=? AND comment_id=?;
SELECT comment_key,ts,text FROM comment
WHERE source_id=? AND post_id=? AND comment_id=?;
```

Фиксированные идентификаторы и ручные ответы находятся в `LABELS`, `SPANS`, `COMMENTS`, `POS`, `NEG`. Это декларации выборки, а не классификатор произвольных публикаций. Обнаруженные исходные тексты не исправлялись, в том числе опечатки, спорные утверждения, даты и цены. Это фиксация содержания источников, не внешняя проверка истинности новостей.

## Формат и смысл меток

- `posts.jsonl`: ключ `id=p<raw_item.id>`, источник, канал, external_id, ссылка, timestamp, точный читаемый `text` и `text_raw` — строка `payload.text` без изменений после единственного разбора внешнего JSON. Некоторые payload содержат дополнительное JSON-экранирование; для читаемого `text` снимается один такой слой, без нормализации пробелов/пунктуации. `text_raw` обеспечивает точную сверку с базой.
- `expected.topics` — **темы проверочного запроса**, включая отрицательные примеры, а не утверждение тематической релевантности. `relevant_news` относится к этим темам. Событие другого предмета может иметь `event_id` при `relevant_news=false` (Balancer в проверке ETH, лонг BTC в проверке ZEC).
- Новость включает конкретное изменение, ценовой алерт или атрибутированное заявление. Самостоятельная идея ТА/прогноз без нового сообщения о заявлении — позиция, не событие. NFT-события входят в широкий охват экосистемы ZEC/Arc, но их проблемы не приписываются базовой сети. Косвенное упоминание сети как площадки DEX само по себе недостаточно.
- `segments` — проверочные фрагменты основания, не обязательное исчерпывающее разбиение текста. Индексы `start/end` относятся к Unicode-символам `text`, диапазон `[start,end)`. Фрагменты могут перекрываться: сообщение о событии одновременно может быть пересказом. `author_position` — позиция автора публикации; цитируемое чужое заявление помечается событием/распространением, не собственным мнением канала. `promo_service` включает рекламу, приглашения и служебные таблицы котировок.
- `event_id` — основной эпизод; `event_ids` дополнительно фиксирует явно размеченные вторичные эпизоды (например, p446 содержит и голосование, и цену 1400). Список не является полным каталогом всех событий многотемных дайджестов. В парах сравнивается основной эпизод; отрицательные пары не имеют общих размеченных вторичных событий.
- `origin` и `source_role` — предварительная оценка наблюдаемой публикации/канала по форме и атрибуциям, не доказательство личности или независимости источников. `repost` у двух точных копий означает текстовую перепечатку, не подтверждённый Telegram forward. Более ранняя копия не объявляется первоисточником. Официальных каналов с подтверждённой принадлежностью здесь нет.
- `comments.jsonl`: точный `comment.text`, ссылка на пост, родитель и его доступный текст/время. `link_target` различает событие, авторский тезис, проект, другой предмет и воздержание. `subject` уточняет предмет. Для `project` речь идёт о Zcash в целом. Неизвестные авторы не объединяются; атрибуция авторов не оценивалась.
- `stored_comments=0` означает «в базе реакция не найдена», а не «аудитория не отреагировала». Полнота сбора комментариев этим числом не гарантируется.

## Окна и перенос

`windows.json` задаёт UTC и полуоткрытые интервалы `[start,end)`. Полное окно покрытия — 9–23 сентября включительно. Узкие окна имеют начало/конец точно на времени реальных публикаций; `boundary` и `window_membership` в постах фиксируют ожидаемое включение. Дополнительные пробы проверяют конец окна за секунду до, точно в момент и через секунду после поста. При равенстве началу пост включается, при равенстве концу исключается. Границы намеренно подобраны по данным, не изображают естественные суточные окна.

Ноябрьское обновление в тексте сентябрьского поста — план, а не ноябрьская публикация. При replay группировать можно только доступные на cutoff публикации. Положительная пара p3900/p745 не разрешает использовать p745 в более раннем окне. Комментарии фильтруются по собственному времени; наличие их в полном файле не разрешает показывать их до публикации.

`holdout.json` резервирует **AAVE, [2026-09-22, 2026-09-24) UTC**. Только ключ темы, алиас и окно; разметки ответов нет. AAVE отсутствует среди подготовленных ZEC/ETH-срезов и в темах этой выборки. Проверено только наличие кандидата в базе, его содержание не размечалось. Эта тема/период не использовалась для настройки в данной задаче; использование другими сессиями вне предоставленного реестра не может быть удостоверено. Всем последующим настройщикам следует исключить этот резерв целиком из tuning и открыть его только после фиксации правил.

## Ограничения проверки

Маленькая целевая выборка измеряет готовность на этих примерах, не общерыночное качество. Связь комментарий→событие представлена одним однозначным примером; высокий процент на нём не доказывает перенос. Официальные источники, идентичность авторов, независимость подтверждений и истинность утверждений во внешнем мире здесь не проверены. Проверка самих продуктовых метрик не выполнялась: задача B фиксирует ожидаемые ответы до настройки. Чужие файлы и код продукта не менялись; git commit/stash/checkout/reset не выполнялись.
