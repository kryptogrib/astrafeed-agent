# Crowd Pulse — план MVP: живая повестка Telegram

## Актуальный контракт

Этот раздел заменяет прежний план Pulse комментариев. Он определяет новую первую поставку; нижележащие материалы сохранены как история решений и экспериментов и не являются текущим объёмом продукта.

### Цель и границы

Рабочий REST API в существующем локальном Docker показывает, какие сюжеты возникают и набирают внимание в наблюдаемых каналах, что о них пишут и где проверить источники. Пользователь получает повестку, выбирает или ищет сюжет, затем читает утверждения и исходные публикации.

- Окна: последние 24 часа и предыдущие 24 часа.
- Форматы: JSON и короткий Markdown на русском.
- Основные данные: публикации из объединения `channels` и `news_channels`.
- Комментарии — отдельный последующий этап, не критерий готовности этой поставки.
- Настроение рынка, сайт, платежи и произвольные исследовательские вопросы исключены. Для подачи OKX Dev Day добавлен тонкий A2MCP-интерфейс к тому же снимку и публичный HTTPS URL.
- Рабочий код размещается в основном пакете с существующим разделением `domain / ports / adapters / application`; исследовательские скрипты остаются материалом для переноса проверенных решений.

### Поток обработки

Сбор публикаций и изменений → точная дедупликация текста → открытое извлечение фрагментов, сущностей и утверждений → эмбеддинги и поиск кандидатов → сопоставление сущностей и назначение сюжетов → проверка источников → расчёт показателей → публикация согласованного снимка.

#### Сбор и повторное использование анализа

- Каждые пять минут собирать объединение двух списков каналов, устраняя дубли по Telegram ID.
- При первом запуске загрузить 48 часов; далее пересканировать это окно для обнаружения новых и изменённых текстов. Соблюдать существующие ограничения Telegram и статусы полноты.
- Хранить версии публикаций: ID, текст, хеш, время публикации, время обнаружения версии, канал и ссылку.
- Ключ анализа — ID публикации, хеш текста и версия классификатора. Одинаковый текст анализировать один раз, сохраняя все места публикации. Повторно использовать только не зависящий от времени результат извлечения; «сегодня» и «вчера» определять отдельно для каждого экземпляра.
- Изменённая публикация замещает предыдущую версию только в новых снимках.

#### Открытое извлечение

Один structured LLM-вызов анализирует пост без обязательной темы или словаря тикеров и возвращает содержательные фрагменты; упомянутые сущности с исходным написанием и контекстом; тип утверждения (событие, позиция автора, явный призыв); говорящего (автор, цитируемый участник, неизвестно); точную цитату и её границы; явно указанные даты и числовые значения с единицами. Алиасы служат подсказками для последующего сопоставления, а не условием допуска к анализу.

Дайджест делится на самостоятельные утверждения. Реклама маркируется на уровне фрагмента и не исключает весь пост. Таблицы цен и фоновые упоминания не становятся событиями автоматически. Код проверяет `quote == text[start:end]`; исправлять границы можно только при единственном точном вхождении цитаты. Неподтверждённое утверждение не публикуется. Ошибка обработки отличается от успешного результата без содержательных утверждений.

#### Эмбеддинги и кандидаты

Использовать внешний API через существующий OpenRouter. Начальная модель — `openai/text-embedding-3-small`, размерность 1536 ([документация OpenRouter](https://openrouter.ai/docs/api/api-reference/embeddings/create-embeddings)). Векторизовать содержательные фрагменты вместе с сущностями, а не дайджест целиком. Кешировать по тексту входа, модели и версии подготовки. Хранить векторы в SQLite; для объёма MVP выполнять точный поиск косинусной близости в памяти, без отдельной векторной БД.

Кандидаты — объединение первых десяти семантически похожих фрагментов и первых десяти результатов поиска по названиям, алиасам и словам утверждения. Для назначения сюжета искать среди фрагментов предшествующих 48 часов; публикации обрабатывать последовательно по времени и стабильному ID. Близость векторов служит только отбору кандидатов и не доказывает совпадение сущности, события или независимое подтверждение. При недоступности embeddings API публикация остаётся в очереди; незаметно переключаться на другой алгоритм нельзя.

#### Сущности, сюжеты и события

Хранить раздельно сущность (например, Ethereum), сюжет (потоки ETH ETF), событие (отток за конкретную дату) и позицию (автор считает отток признаком слабого спроса).

После открытого извлечения отдельный structured вызов получает новые утверждения и найденных кандидатов, сопоставляет сущности и назначает сюжет. Допустимые решения: существующий объект, новый объект или неоднозначность.

- Совпадение тикера не объединяет сюжеты. Неоднозначную сущность хранить отдельно; похожее написание автоматически не становится подтверждённым алиасом.
- Один пост может участвовать в нескольких сюжетах через разные фрагменты. У сюжета стабильный ID, краткое русское название и описание границ.
- Противоположные позиции могут относиться к одному сюжету, сохраняя авторство и различия. Разные даты, суммы и участники остаются отдельными событиями.
- Пересказы связывать в одно событие только при совместимости существенных атрибутов и положительном решении модели. При сомнении оставлять события раздельными внутри общего сюжета.
- Автоматическое глобальное объединение существующих сюжетов отложено; ошибки дробления измеряются на проверочной выборке.

Цитата подтверждает наличие высказывания в источнике, а не истинность события. Число каналов характеризует распространение, а не количество независимых подтверждений.

### Повестка и показатели

Для времени снимка `T`: текущее окно `[T−24h, T)`, предыдущее `[T−48h, T−24h)`. Кодом считать публикации, уникальные каналы, точные повторы и связанные пересказы. Один канал даёт сюжету не более одного голоса за окно.

Сравнивать общий набор каналов с полным сбором и успешной обработкой обоих периодов. Успешно проверенное отсутствие публикаций — ноль; ошибка или необработанный пост означает неполноту. Новый канал допускается к сравнению после полного бэкфилла обоих окон.

Основная выдача — до десяти новых или растущих сюжетов, минимум по двум каналам в текущем окне на сопоставимом наборе. Сортировка: прирост каналов, текущее число каналов, свежесть, стабильный ID. «Новое» означает ноль в предыдущем полном окне; `first_seen` — первое обнаружение в нашей базе.

Если сопоставимых каналов меньше двух, возвращать доступные сюжеты, наблюдавшиеся минимум в двух каналах, без утверждения о росте (`growth=null` с причиной ограничения). Одноканальные сюжеты доступны через поиск. Если полноценное сравнение не выявило роста, возвращать честную пустую повестку.

Карточка содержит название, сущности, показатели, объяснение изменения и до трёх утверждений с цитатами и ссылками. Русский пересказ не добавляет числа или детали, отсутствующие в привязанных цитатах.

### Хранение и согласованность

Добавить версионируемые результаты извлечения, сущности, сюжеты, события, связи, кеш эмбеддингов и снимки. Снимок фиксирует конкретные версии публикаций, результатов, названий, связей и показателей и публикуется атомарно. Незавершённый цикл не заменяет предыдущий снимок. Исторический снимок не меняется после редактирования поста, появления будущих сообщений или обновления классификатора.

### REST-интерфейсы

- `GET /agenda`
- `GET /stories/search?q=…`
- `GET /stories/{id}`

Общие параметры: `format=json|md` и необязательный `snapshot_id`. Без него выбирается последний опубликованный снимок; каждый ответ возвращает использованный ID.

Поиск — SQLite FTS5 по названиям, сущностям, алиасам, утверждениям и текстам публикаций текущего окна. Точное совпадение названия выше остальных, далее полнотекстовая релевантность. Возвращать совпавшие фрагменты. Пагинация: `limit=10`, `offset=0`, максимум `limit=100`.

Карточка раскрывает события, позиции и исходные публикации того же снимка. Неизвестный снимок или сюжет — `404`; до первого снимка — `503` с явным статусом `preparing`.

Каждый ответ показывает время среза, успешного сбора и анализа, полноту источников, очередь и ограничения. После 15 минут без успешного обновления снимок помечается `stale`.

### Фоновый цикл и бюджет

Цикл: сбор → ограниченно параллельное извлечение из независимых публикаций → назначение сюжетов → построение снимка. `backfill_hours` задаёт глубину сбора и загрузки публикаций (не меньше 48 часов), а окна сравнения остаются двумя сутками по 24 часа. `agenda.extract_concurrency` (по умолчанию 12) ограничивает число одновременных извлечений; одинаковый текст использует один кешированный результат. `agenda.assign_concurrency` (по умолчанию 16) ограничивает число одновременных предложений модели. Эмбеддинги новых фрагментов отправляются пакетами до 64 и кешируются по точному входу.

`agenda.assignment_mode=auto` выбирает строгий режим для очереди меньше 128 публикаций и быстрый режим для большого бэкфилла. В строгом режиме перед сохранением каждого предложения код заново рассчитывает полный набор кандидатов и контекст относительно уже сохранённых предыдущих публикаций; изменившееся решение модели пересчитывается. В быстром режиме решения принимаются против замороженного контекста батча без повторов, а новые сюжеты сопоставляются при одинаковой ключевой сущности и косинусной близости центроидов не ниже `agenda.merge_cosine_threshold` (по умолчанию 0,92). Это ускоряет загрузку истории, но может ошибочно объединить сюжеты; после бэкфилла требуется проверка карточек и 60-постовой выборки. Режим можно явно поставить в `strict` или `relaxed`.

Во время долгого анализа первый промежуточный снимок публикуется после первого батча, затем каждые 200 постов или 10 минут, с `processing_in_progress` и показом неполноты; окончательный снимок не перезаписывает промежуточный. HTTP-запросы не вызывают LLM. Все платные вызовы, включая эмбеддинги, повторы и исправления structured output, проходят через общий дневной бюджет $5. Резервации в SQLite атомарны (`BEGIN IMMEDIATE`); отменённый после резервации вызов оставляет консервативную запись расхода.

При исчерпании бюджета сохранять очередь и последний снимок. После перезапуска продолжать с сохранённых результатов, не оплачивая повторно кешированные этапы. В `/healthz` показывать commit, состояние цикла, последнюю ошибку, последний снимок и бюджетную блокировку. Старые API сохранить.

### Этапы и критерии проверки

1. **Хранение и открытое извлечение.** На сохранённых публикациях получить проверенные фрагменты, сущности и утверждения; подтвердить повторное использование анализа и корректность версий.
2. **Кандидаты и сюжеты.** Подключить эмбеддинги, сопоставление сущностей и назначение сюжетов; затем показатели двух окон и неизменяемый снимок.
3. **API и поиск.** Пройти сценарий «повестка → поиск → карточка → источник» на одном снимке.
4. **Живой Docker.** Подключить сбор обоих списков каналов, очередь, бюджет и восстановление после перезапуска.
5. **Приёмка и демонстрация.** Зафиксировать результаты, ограничения и воспроизводимые команды.

Проверку качества проводить на отдельной выборке минимум из 60 публикаций двух периодов. До прогона зафиксировать ожидаемые сущности, существенные утверждения, принадлежность сюжетам и десять поисковых запросов. Включить неизвестные проекты, дайджесты, рекламу, мнения, пересказы и разные события одной сущности. Старую transfer-выборку использовать только для регрессий.

Критерии:

- Все опубликованные цитаты и числа прослеживаются до исходников; агрегаты пересчитываются кодом.
- Не менее 18 из 20 заранее выбранных включений в сюжеты корректны.
- Каждый тезис первых десяти карточек подтверждён источником.
- Релевантный сюжет попадает в первые пять результатов минимум для восьми из десяти запросов, если материал существует.
- Отдельно публикуются полнота извлечения и доля пропущенных объединений; пустая выдача не считается доказательством качества.
- Добавление канала, повтор поста и будущие сообщения не создают искусственный рост.
- Новая публикация появляется в следующем успешно обработанном снимке; рестарт не создаёт дубли.
- Сбой API, Telegram или бюджета виден в статусе и не превращается в нулевую активность.

Разметка агента предварительная. Владелец просматривает первые карточки и подтверждает их полезность для демонстрации.

После работающей первой поставки можно добавить отдельную очередь комментариев с меньшим приоритетом. Анализировать их с контекстом поста и цепочкой предков; вопросы и реакции хранить отдельно. Не включать комментарии в число каналов сюжета и не назначать конкретный тезис без подтверждённой связи.

### Цель демо

**За один вызов понять, что изменилось в обсуждении темы за 24 часа, почему люди так реагируют и какие сообщения подтверждают вывод.** Первый пользователь — человек или исследовательский агент, которому нужно быстро разобраться в реакции на событие. Telegram — первый источник, расширение платформ следует после проверки качества.

Из трёх вариантов — общий индекс настроения, детектор координации, объяснение изменений — рекомендуем третий. Индекс сам по себе плохо объясняет причины; детектор координации требует отдельной разметки и проверки. Жалобы и вопросы остаются частью ответа как высказывания участников. Обещание опережать новости не является условием успеха демо.

### Что фактически готово

- В `astrafeed.db`: 13 815 постов за 9–23 сентября, 20 источников в каталоге, записи постов у 19. Это не 20 активных обсуждений.
- Сохранённый payload содержит текст, ссылку, время и данные канала. Текстов комментариев, их классификации и почасовых Pulse-агрегатов в этой БД пока нет. Число ≈1437 в старом чеклисте не подтверждает наличие скачанного корпуса комментариев.
- Один канал содержит 9523 из 13 815 постов. Объём постов нельзя выдавать за разнообразие участников или объём обсуждений.
- Есть Telegram-метод чтения комментариев с состояниями полноты, модели комментариев с контекстом ответов, SQLite, structured LLM и контроль бюджета. `fetch_comments_detailed` пока не принимает `min_id`; это доработка, а не готовая возможность.
- HTTP пока даёт `/healthz`; Pulse, Trending и MCP предстоит реализовать. Записи полноты постов не доказывают полноту комментариев.

### Очерёдность и проверяемые результаты

1. **Корпус обсуждений.** На небольшой выборке постов проверить доступность тредов, затем сохранять комментарии доступных каналов за то же 14-дневное окно. Хранить ID/peer, post/thread, текст, время, ссылку, родительский ответ и статусы сбора. Бэкфилл возобновляемый; повторный запуск не размножает записи. Исторический проход отделить от live-пересканирования последних 48 часов. Результат: число реально сохранённых комментариев по каналам/дням, список неполных тредов и 2–3 темы-кандидата для демо. До этого объём пригодных данных неизвестен.
2. **Проверка смысла на 100–200 комментариях.** Для каждого примера давать классификатору комментарий, пост и доступный родительский ответ. Извлекать тему, отношение именно к этой теме, тип и краткий аргумент; каждое утверждение связывать с ID исходного комментария. Допускать неизвестную тему/отношение вместо угадывания. Разметить обычную выборку и отдельно сложные примеры/жалобы, не смешивать их частоты. Результат: человеческая проверка тематической привязки, ложных жалоб, пропусков и соответствия аргументов цитатам; стоимость обработки. Модель не утверждает собственную разметку за человека.
3. **Один Pulse за 24h.** На проверенном корпусе выдать JSON и бриф: что обсуждают, что изменилось, аргументы, вопросы/жалобы, ссылки и coverage. Числа считаются кодом. Сначала сравнение с предыдущими 24h; исторический baseline показывать только при достаточной сопоставимой истории. Результат: один реальный ответ, каждое ключевое утверждение которого можно проверить, плюс пример честного ответа при нехватке данных. Не ждать полноценного HTTP для первой проверки полезности.
4. **Повторяемый сервис и Trending.** Запустить обновление комментариев; построить почасовые агрегаты и ранжирование на тех же метриках. Trending возвращает до 10 тем с достаточными данными, без заполнения пустого списка выдуманными сигналами. Публикации и комментарии считаются раздельно. Для устойчивости сравнивать одинаковый набор источников либо явно отмечать изменение охвата. Результат: повторный сбор идемпотентен, изменение ответа объясняется новыми данными, а не случайной генерацией.
5. **Публичное демо и подача.** REST с настоящим вызовом, бриф с источниками, состояние свежести данных, воспроизводимые команды и проверки. Подготовить 2–3 реальных примера: реакция на событие, изменение дискуссии, недостаток данных. Для replay фиксировать время среза и не использовать будущие сообщения. MCP — следующий тонкий интерфейс при наличии времени; x402 — после полезного работающего сервиса.

Если комментариев мало даже для 24h по отдельным темам, сначала выбрать каналы с живыми обсуждениями и повторить проверку корпуса. Снижать пороги ради красивой цифры или подменять мнение участников тоном новостных постов нельзя. Качественная сводка нескольких реплик допустима с явным указанием малой выборки и без надёжного mood-score.

### Что уточнить в прежних контрактах перед реализацией

Определения счётчиков, знаменателей и уровней дедупликации: [метрики первого Pulse](../research/pulse-metrics-mvp.md). Это предложение для реализации, а не уже измеренные показатели.

Уточнение владельца: фиксированный набор тем для демо не подходит. Начали с открытого обнаружения сущностей без LLM на реальной базе: [результаты и воспроизводимый probe](../research/entity-probe-findings.md). Словарь кандидатов пополняется из корпуса; похожие написания и контекст поста пока дают кандидатов, а не автоматические подтверждённые entity-метки.

- Первый интерфейс — `pulse(topic, window=24h)`; `1h` после проверки плотности данных, `7d` позже. Trending делать после полезного Pulse.
- Контекст поста и родительского ответа обязателен для интерпретации коротких реплик. Нейтральное отношение и неизвестное отношение — разные состояния.
- У mood и сравнения активности могут быть разные статусы доступности. Проверять полноту предыдущего окна, а не только baseline и текущего числа комментариев.
- Сохранять оригиналы и evidence-ссылки рядом с агрегатами. Не применять к комментариям новостной фильтр, который удаляет сообщения с общей ссылкой: одна ссылка может сопровождать разные мнения. Копии маркировать, сохраняя происхождение; несколько каналов не доказывают независимость свидетельств.
- `first_seen` означает первое найденное в наблюдаемых данных. Время публикации и время фактического обнаружения различаются. Первая новость среди наших каналов не равна первой новости вообще.
- На первом проходе достаточно одного structured LLM-классификатора; новые модели, embeddings, SimHash и векторная БД добавляются только по измеренной необходимости.

### Ограничения хакатона, которые меняют приоритеты

На [странице X-Agent](https://xagt.ai/hackathon?lang=en) период регистрации/сборки указан как 2–19 сентября, проверка — 20 сентября – 1 октября, результаты — 2–4 октября. Для этой команды используем уточнение владельца: **сдать проект до 25 сентября 2026**. Повторно запрашивать подтверждение даты не нужно; точное время и часовой пояс пока неизвестны.

Для этого продукта предлагаем Open Innovation. Правила исключают security/audit, exploit/scam/rug-pull detection и близкие сервисы. В объём демо включается анализ реакции и вопросов пользователей; функции обнаружения атак, оценки безопасности кошельков и скама исключаются по существу, а не только из названия.

[Официальный репозиторий подачи](https://github.com/xagentAI/xagt-plugin) требует работающий публичный API, health с точным commit, deployment proof, полный исходный код и воспроизводимую проверку. Собственный MCP и x402 при подаче не обязательны. Поэтому развёртывание и проверяемый API приоритетнее платежей и отдельного MCP-сервера. Дата сдачи уточнена владельцем; соответствие проекта условиям проверяется при подготовке подачи.

## Контекст
Движок AstraFeed уже умеет: читать Telegram-каналы, забирать комментарии с честным статусом (`TelegramSource.fetch_comments_detailed`, `adapters/source/telegram.py:467` → `CommentFetch` со `status/possibly_truncated/raw_count`), вызывать LLM со structured output (`_wrap_with_instructor`, `adapters/llm/openrouter.py:437`) под глобальным дневным бюджетом (`adapters/llm/budgeted_client.py`), хранить в SQLite и крутить polling + FastAPI (`cli.py:_poll/_serve`).
Цель: к концу дня 2 — `trending` и `pulse(topic, window∈{1h,24h})` через REST + MCP на реальных 10+ каналах. **Принцип: лучше честное «данных недостаточно», чем уверенная цифра на неполных данных.**

Решения: темы — гибрид (LLM → нормализация + алиасы из config); REST + MCP; **x402 вне обязательного объёма**; окно `7d` — вне MVP.

## Контракты (фиксируем до кода)

**Окна** (W ∈ {1h, 24h}, t = now, округлённое вниз до часа для агрегатов):
- current = `[t−W, t)`, previous = `[t−2W, t−W)`
- baseline = почасовое среднее за `[t−W−7d, t−W)` — **не включает текущее окно**, всплеск не поднимает свою «норму».
- Нужно истории: 7d + W. Бэкфилл = 8 дней.

**Полнота данных** — каждый ответ содержит `coverage`:
`{channels_ok, channels_failed, threads_truncated, comments_unclassified, history_hours, baseline_hours}`.
- `baseline_hours < 72` → `vs_baseline: null`, `status: "insufficient_history"`.
- baseline = 0 → `vs_baseline: null` + `new_topic: true` (не ∞, не x0).
- `n_current < min_comments` (напр. 20) → `mood: null`, `status: "insufficient_data"`.
- Час, в котором был сбой сбора (flood-wait/error), помечается `incomplete` и исключается из baseline.

**Sentiment на уровне темы**: LLM возвращает `mentions: [{topic, sentiment, kind}]` + общий `gist`. «SOL работает отлично, ETH опять дорогой» → SOL:bull, ETH:bear. Агрегируем по `(comment, topic)`.

**Сбор = пересканирование тредов, а не только новых постов**: поздний комментарий к посту 20-часовой давности — нормальная ситуация. Для каждого поста за последние 48ч храним `thread_state(post_key, max_comment_id, last_scan, status)` и при каждом цикле дочитываем `min_id > max_comment_id`. Посты старше 48ч считаются «замороженными» (документируем ограничение).

**Идемпотентность**: `comment_key = peer:comment_id` (uq). Агрегаты `topic_hour` пересчитываются из `comment_mention` для затронутых часов, без инкрементов. Повторный бэкфилл даёт тот же результат.

**Бюджет**: классификатор ходит только через `BudgetedClient`; перед бэкфиллом оценка `N_comments × avg_tokens × price` в dry-run; при исчерпании бюджета комменты остаются `unclassified` и видны в `coverage`.

**Демо-заявление**: «комьюнити раньше новостей» показываем как **ретроспективный replay** на бэкфилле с явной подписью. Про «live early alert» говорим, только если поймаем такой случай вживую.

## День 1 — сбор → хранение → числовой REST

1. **Схема и порт** (`ports/pulse.py`, `adapters/repository/sqlite/models.py`, in-memory по образцу `adapters/repository/memory.py`):
   `comment(comment_key uq, post_key, channel, ts, text, classified)`, `comment_mention(comment_key, topic, sentiment, kind)`, `comment_gist(comment_key, gist)`, `thread_state`, `collect_hour(channel, hour, ok|incomplete)`, `topic_hour(topic, hour, n, bull, bear, neutral, questions, complaints, shills, channels)`.
2. **Сборщик** `application/pulse_ingest.py`: посты за 48ч → `fetch_comments_detailed` с `min_id` → upsert comments + `thread_state` + `collect_hour`. Статусы `FLOOD_WAIT/ERROR` → `incomplete`, никогда не «0 комментов».
3. **Возобновляемый бэкфилл** `astrafeed-pulse backfill --days 8`: чекпоинт по каналу/посту, безопасен к повторному запуску. **Запустить сразу, как заработает сырой сбор (ещё без классификатора)**, чтобы копил, пока пишется остальное.
4. **Классификатор** `adapters/llm/comment_classifier.py`: Pydantic batch-схема (mentions + gist), cheap_model, батчи ~40, через `BudgetedClient`; `StubCommentClassifier` для тестов/`--stub-llm`. Отдельный шаг `classify-pending` проходит по `classified=0`.
5. **Нормализация тем** `pulse/topics.py`: upper, strip `$`, `topic_aliases` из config.
6. **Мини-разметка**: 50–100 комментов в jsonl, глазами проверить `complaint` и per-topic sentiment.
7. **Числовой REST**: `pulse/service.py` (окна, baseline, coverage, статусы) + `GET /pulse`, `GET /trending` в `adapters/http/app.py`. Без LLM-брифа.

## День 2 — MCP → replay-демо → LLM-brief

8. **MCP**: зависимость `mcp` (FastMCP), `adapters/mcp/server.py`, tools `trending` / `pulse` поверх того же сервиса, смонтировать в uvicorn из `_serve`.

## Проверка
Юнит-тесты на in-memory store (`make test`):
- поздний комментарий к старому посту попадает в свой час при повторном скане;
- обрезанный тред (`possibly_truncated`) и flood-wait → `coverage`, час `incomplete`, исключён из baseline;

- неполная история → `insufficient_history`, `vs_baseline: null`;
- границы часов (коммент в `hh:59:59` / `hh:00:00`), current не пересекается с baseline;
- нулевой baseline → `new_topic`, не ∞;
- мульти-тема с разным sentiment агрегируется раздельно.
Интеграционно: `backfill --stub-llm` → реальный LLM на 1–2 каналах (сверить стоимость) → `make serve` → `curl /trending`, `curl '/pulse?topic=SOL&window=24h'` → MCP Inspector → `make check`.
