# Pulse: дедупликация и метрики первого демо

Предложение от 23 сентября 2026 для срока сдачи 25 сентября. Это определения для следующего этапа, не реализованные метрики и не измеренные результаты.

## Три разные операции

1. **Идемпотентность загрузки:** одно сообщение определяется `(platform, peer_id, message_id)`. Повторная загрузка обновляет запись. Редактирование инвалидирует прежнюю классификацию. Связь с тредом хранится отдельно; один комментарий не размножается из-за повторного чтения.
2. **Совпадение текста:** существующий `src/astrafeed/textkey.py` нормализует регистр/пробелы и считает SHA-256. Хеш подходит для поиска одинакового нормализованного текста. Сохраняем все сообщения и их происхождение, добавляя группу совпадений. Одинаковое «да» в разных тредах не доказывает копипаст или одно мнение.
3. **Сходство аргументов:** «комиссия выросла» и «комиссия не выросла» похожи по словам, но противоположны по смыслу. Семантические группы нужны для сводки, а не удаления сообщений. В MVP группировать извлечённые аргументы в рамках темы с сохранением ссылок на каждый источник.

Новостной `prefilter/Deduper` отбрасывает сообщения с общей ссылкой: напрямую к комментариям его не применять. Не удалять отрицания, числа, тикеры и эмодзи при нормализации ради повышения совпадений. Кеш классификации должен учитывать комментарий, контекст поста/ответа, версии схемы/промпта и модель — одного текстового хеша недостаточно.

## Что сохранять при сборе

ID источника и треда, ID комментария, текст, permalink, `published_at`, `collected_at`, `edited_at`, доступный `author_key`, `reply_to_id`, контекст поста/ответа. Отдельно — журнал сканов: запрошенные границы, статус, лимит, число записей, обрезка, отсутствующий контекст и время последнего успешного скана. Неизвестные авторы остаются неизвестными, а не объединяются в одного автора.

## Метрики ответа: тема × окно

Единица счёта — уникальная пара `(comment_id, topic_id)` после устранения повторных загрузок. Исходные сообщения сохраняются, одинаковые тексты разных сообщений остаются в наблюдаемом объёме. Посты и комментарии считаются раздельно.

| Поле | Определение и ограничение |
|---|---|
| `comments` | Число комментариев, отнесённых к теме. Это наблюдаемая активность, не число людей или независимых мнений. |
| `authors_known`, `author_coverage` | Число разных доступных ключей авторов; доля комментариев с известным автором. Один ключ не гарантирует одного человека. |
| `threads`, `sources` | Разные discussion-треды и исходные каналы. Несколько каналов не означают независимые свидетельства. |
| `top_source_share` | Комментарии из крупнейшего по этой теме источника / все комментарии темы. Показывает концентрацию выборки. |
| `text_repeat_share` | `(N − distinct(normalized_text_hash)) / N` среди непустых текстов темы в окне. Доля повторов текста, не вероятность ботов/координации. Короткие ответы могут повторяться естественно. |
| `sentiment_counts` | Числа bull/bear/neutral/unknown по теме. Для неторговых тем заранее определить смысл отношения; недовольство сервисом не автоматически прогноз падения токена. |
| `mood_score` | `(bull − bear) / (bull + bear + neutral)`. Unknown не включать в знаменатель, его долю показывать отдельно. При недостатке данных — null. Это баланс классифицированных реплик, не вероятность движения цены. |
| `complaints`, `questions` | Числа классифицированных жалоб и вопросов. Долю считать только среди сообщений с определённым типом и публиковать знаменатель/долю неклассифицированных. Если типы взаимоисключающие, явно назвать правило выбора основного типа. |
| `activity_vs_prev`, `mood_delta` | `N_current / N_previous` и `score_current − score_previous` на сопоставимых полных окнах и одном наборе источников. Если previous=0, отношение null с явным признаком нулевого предыдущего объёма; это ещё не доказательство новой темы. |
| `arguments`, `top_questions` | Сводки с evidence ID/ссылками и числом поддерживающих комментариев. Отдельно проверять, что процитированные сообщения действительно поддерживают формулировку. |

Первые показатели считать за 24h и предыдущие 24h. Baseline добавить после сбора сопоставимой истории: `N_current / (среднее число комментариев за полный час истории × часы текущего окна)`. Применять пороги полноты из плана; при нуле нормы или недостатке истории — null. Ошибка сбора не равна нулевой активности.

Порог вроде 20 комментариев — инженерный ограничитель, не статистическая гарантия. Много реплик одного автора/треда также не делает настроение репрезентативным. При малой выборке показывать цитаты и качественную сводку с ограничением вместо уверенного score.

## Метрики качества данных и сервиса

- **Сбор:** число запланированных/успешно проверенных тредов; отдельно empty, unavailable, error, flood-wait и truncated. Доля успешных проверок не доказывает полноту всех существующих комментариев.
- **Классификация:** pending/failed/classified; missing-context; unknown-topic и unknown-sentiment среди обработанных. Они показывают, какая часть корпуса не участвует в выводе.
- **Свежесть:** время последнего успешного сбора по источнику и возраст данных ответа. Live-задержку считать отдельно от исторического backfill.
- **Цена и скорость:** входные/выходные токены, фактическая стоимость на 1000 классифицированных сообщений, длительность обработки и ответа Pulse, cache hit rate. При неизвестной цене значение null.

Для клиента достаточно coverage, статуса свежести и размера выборки; внутренние счётчики хранятся для диагностики. На первом этапе достаточно SQL-отчёта/логов, отдельный monitoring-стек не требуется.

## Ручная проверка 100–200 примеров

Сделать обычную выборку по разным каналам/дням и отдельный набор сложных примеров. Часть примеров оставить для финальной проверки после настройки промпта. Показывать числа проверенных примеров, а не только проценты.

- **Complaint precision:** верные жалобы / все предсказанные жалобы; **recall:** найденные жалобы / все размеченные жалобы. При нулевом знаменателе — null.
- **Темы:** precision/recall по парам комментарий–тема; отдельно ошибки переноса темы из родительского поста.
- **Sentiment:** матрица ошибок по классам, отдельно нейтральное и неизвестное. Общая accuracy может скрывать провал на редких классах.
- **Основания:** число проверенных выводов, действительно поддержанных источником / все проверенные выводы; отдельно инверсии смысла и выдуманные утверждения. Для демонстрируемых ключевых выводов проверить каждую ссылку вручную.
- **Дедупликация:** повторная загрузка не увеличивает число уникальных ID. Для любых fuzzy-слияний отдельно разметить пары и измерить ложные объединения, включая противоположные мнения и короткие ответы.

## Компоненты

Сейчас: существующий Telethon/SQLite/хеш, structured LLM и JSONL для разметки; [Label Studio](https://github.com/HumanSignal/label-studio) — готовый открытый интерфейс разметки текста, если ручной JSONL неудобен.

Позже при измеренной проблеме копипаста: [simhash-py](https://github.com/seomoz/simhash-py) для near-duplicates или [datasketch](https://github.com/ekzhu/datasketch) с MinHash/LSH для поиска похожих наборов текстовых фрагментов. Порог и подготовку текста проверять на своих парах. Эти библиотеки не определяют независимость мнений.

Для смысловых групп: [Sentence Transformers paraphrase mining](https://www.sbert.net/examples/sentence_transformer/applications/paraphrase-mining/README.html) даёт кандидатов на сходство; пригодность модели для русского/криптосленга и сохранение противоположных позиций проверяются отдельно. До первого Pulse эти зависимости не обязательны.
