# Проверка готовности основной фичи Pulse

24 сентября 2026. Проверял основной ассистент лично, без делегирования. Проверяется реализация фичи, не актуальные формальные правила хакатона. Код продукта не изменён, платных вызовов не было.

## Вердикт

Работает воспроизводимое исследовательское демо по двум подготовленным темам. Источники и подсчёты имеют проверяемую основу. Однако до демонстрации произвольных окон необходимо устранить утечку текста из будущих сообщений. Текущая реализация ещё не отвечает на «что изменилось» и не обрабатывает новую тему сквозным автоматическим процессом. Отсутствие LLM на HTTP-запросе само по себе нормально: проблема — отсутствие показанного автоматического обновления подготовленных срезов и группировки.

## Что реально проверено

- Запущен отдельный реальный HTTP-сервер: `uv run python3 docs/research/pulse_service.py astrafeed.db 127.0.0.1 18765`.
- Выполнены 44 запроса: темы и алиасы, неверные параметры, JSON/Markdown, пустое окно, каждый день 11–23 сентября, шесть параллельных запросов. Ни одного HTTP 5xx на этих запросах.
- ZEC: 91 опубликованная реплика, 56 единиц, 6 тем; ETH: 21 реплика. Все 112 ссылок, дат и счётчиков авторов единиц сверены с SQLite, расхождений нет. Это структурная сверка, а не независимая смысловая разметка всех 112 реплик.
- Каждый возвращённый timestamp входит в запрошенное дневное окно; сумма опубликованных по непересекающимся дням равна 91. Ошибка окна относится к формулировкам, а не к отбору ID.
- HTTP Markdown ZEC побайтно совпадает с `artifacts/pulse-zec/brief.md`.
- Шесть параллельных ответов одинаковы. Одиночный полный запрос занимал примерно 35–41 мс; пакет из шести — около 2.09 с. Это локальное наблюдение, не нагрузочная гарантия. Полное перечитывание файлов/SQLite при каждом запросе заслуживает внимания после исправления качества.
- `make check`: ruff src/tests, форматирование 92 файлов, mypy 65 исходных файлов, 152 теста — всё прошло. `ruff check .` отдельно нашёл 9 ошибок в tools/comment-review/build.py; они вне штатного охвата make check. Исследовательские docs-скрипты исключены настройками Ruff, 152 теста не означают проверку всего Pulse-процесса. Три HTTP-теста Pulse используют fake_pulse.
- MD5 базы после HTTP-проверок: `8618099125a806df376354286ccd982e`.

## P0: текст не соответствует выбранному окну, в ответ про прошлое попадает будущее

Воспроизведение:

```sh
curl -s 'http://127.0.0.1:18765/pulse?topic=zec&window=2026-09-20..2026-09-20'
```

Единица `wl_deadlines` содержит один источник: `7149/571965`, 20 сентября 12:51, исходный текст «только чекер выкатили».

Но title остаётся: «Дедлайны и чекеры: “дедлайн 4 часа”, ссылка на BiTFoot, чекер zeckers, “выкатили чекер” лягушек, окно WL 72 ч закончилось». Реплики о четырёх часах и окончании 72-часового окна — 21 сентября. JSON и Markdown содержат эту ошибку. В приложенном `artifacts/pulse-critique/zec-sep20.md` виден фактический ответ.

Причина: `pulse_aggregate.py:68` копирует весь объект группировки (`dict(a, ...)`), обновляя ids/счётчики/ссылки, но оставляя title и note полного периода. `pulse_brief.py` также сохраняет заметки тем и групп без проверки их основания в окне.

Минимальное исправление: при частичном составе единицы выводить только формулировки, чьи основания остались в окне, либо перейти к отдельным проверенным пересказам реплик. Временно ограничить публичное демо полным фиксированным срезом, если исправление не готово. Нельзя заявлять причинно корректный replay только после исправления title: классификатор читал полный тред, включая сообщения позже даты replay; влияние этого контекста требует отдельного контроля.

Критерий: в ответе за 20 сентября нет утверждений, основанных только на 21 сентября; контекст вне окна либо явно обозначен с источником и временем, либо исключён. Будущий контекст для replay недопустим.

## P1: даты не валидируются как даты

Все три запроса вернули 200 `no_data_in_window`:

- `window=2026-02-30..2026-02-31`;
- `window=aaaaaaaaaa..zzzzzzzzzz`;
- `window=2026/09/17..2026/09/19`.

Причина: проверяются длина строк и лексикографический порядок (`pulse_brief.build`), а не календарь. Требуется строгий разбор дат, документированная временная зона и 422 для неверного формата/даты. `24h`/`1h` сейчас возвращают 422 — это ограничение контракта, не сбой, но расходится с исходным продуктовым обещанием.

## P1: обычный запуск проекта не включает Pulse

`src/astrafeed/cli.py:190` вызывает `create_app()` без провайдера. Прямой ASGI-запрос к этому приложению дал 404 `/pulse`. Dockerfile запускает `astrafeed-serve` и копирует только src с файлами зависимостей, без docs/research и artifacts. Следовательно, текущий стандартный контейнерный путь не упаковывает это демо. Контейнер не собирался: вывод основан на Dockerfile, entrypoint и воспроизведении приложения.

Нужен один документированный путь запуска/развёртывания именно Pulse, содержащий все нужные файлы. Проверять `/pulse`, а не только `/healthz`, который сейчас отвечает ok без Pulse-провайдера. Публичный адрес пользователь не предоставил, доступность извне не проверялась.

## P1 по продукту: короткий ответ и изменение обсуждений пока отсутствуют

ZEC Markdown содержит 202 строки, 15 588 символов. Раздел «Коротко» перечисляет объём, темы и типы реплик. Чтобы понять реальные позиции и повторяющиеся вопросы, пользователь должен читать длинный отчёт. Это пригодный документ аудита, но слабый первый ответ сервиса.

Для демо нужен отдельный короткий слой: 3–5 содержательных наблюдений с источниками, охватом и оговорками. Например: рыночный спор сосредоточен в одном треде; в нескольких обсуждениях возникают вопросы о кошельках и WL; критика приватности принадлежит одному участнику, утверждение не проверено. Полный отчёт оставить по отдельному полю/формату.

В API нет сравнения периодов, новых/исчезнувших тем, изменения активности или жалоб. Вопрос «что изменилось?» сейчас требует самостоятельного анализа двух ответов. Не надо выдумывать индекс настроения: достаточно одного проверенного сравнения одинакового набора источников за два периода либо явного `change_unavailable`.

BTC даёт 404; поддерживаются только реестровые ETH/ZEC. Это честно указано в ошибке. Подготовленная группировка ZEC создана агентом, ETH выдаёт пересказы отдельных реплик. Следующая тема не проходит этот путь автоматически. Показывать как историческое демо на подготовленных срезах допустимо, как универсальный живой мониторинг — ещё нет.

## P2: прозрачность и удобство

- `$ZEC` и ` ZEC ` возвращают 404; ZEC, zcash, зек, Ethereum работают. Полезна нормализация пробелов/кэштега.
- OpenAPI не описывает форму ответа (`schema: {}`), допустимые темы и формат окна; это мешает внешнему агенту вызвать инструмент с первого раза. Нужны примеры запроса и типизированный результат/список возможностей.
- Исправленные агентом ETH-пересказы помечаются «пересказ модели» функцией auto_grouping. Особенно заметно на 342487/342498, включённых агентским исправлением. Происхождение выводов теряется при отображении; сохранить review provenance и пограничность в API и Markdown.
- Статус ok означает наличие единиц, а не достаточность или проверенность данных. Слой полноты/качества лучше отделить от транспортного успеха; сейчас пояснения есть в длинном отчёте, но машинному клиенту труднее ими воспользоваться.

## Приоритет перед показом

1. Исправить окно и календарную валидацию, добавить интеграционные проверки с настоящими подготовленными срезами.
2. Обеспечить один воспроизводимый запуск сервиса и проверку реального `/pulse` после развёртывания.
3. Добавить короткий содержательный ответ поверх длинного аудита; явно показывать исторический период и подготовленный характер среза.
4. Если остаётся время — одно честное сравнение периодов. Затем автоматизация группировки новой темы. Trending, новые платформы и платёжный слой сейчас менее важны для качества основной фичи.
