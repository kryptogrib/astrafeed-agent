## Факты и воспроизведение

Все подключения к исходной БД — только SQLite URI `mode=ro`, без ORM, миграций и запуска ingestion. MD5 до и после проверки: `8618099125a806df376354286ccd982e`, совпадает с `artifacts/pulse-slices.json`. Сетевых LLM-вызовов не было. Чужие изменения и артефакты не перезаписывались.

SQL ниже выполняется из корня репозитория так:

```sh
sqlite3 -header -column 'file:astrafeed.db?mode=ro' <<'SQL'

```

Для Python использовано `sqlite3.connect(Path('astrafeed.db').resolve().as_uri() + '?mode=ro', uri=True)` и `BEGIN` для согласованного снимка. Проверка хеша читает байты файла, не открывает пишущее соединение:

### Источники и роли


### Что делает текущий Pulse

| Файл | Фактическое поведение |
|---|---|
| `pulse_service.py` | Оборачивает `build`, возвращает JSON/Markdown; темы берёт из реестра подготовленных срезов. Статус зависит от наличия comment units. Проверяет MD5 при старте, внедряет провайдеры в FastAPI. |
| `pulse_brief.py` | Читает `pulse-slices.json`, сохранённые `published.json` и агентскую группировку; для ETH без группировки создаёт одну единицу на реплику. CLI пишет brief/aggregate, `build()` ничего не пишет. |
| `pulse_aggregate.py` | Берёт ID опубликованных комментариев, время/авторов из БД; считает реплики, авторов, треды, каналы, ссылки. Проверяет допустимость ID и отсутствие двойного назначения; качество смыслового объединения не проверяет. |
| `pulse_compare.py` | Сопоставляет два непересекающихся периода, A раньше B; независимо пересчитывает опубликованные реплики по БД и файлам. Это сравнение объёма/состава, не изменение настроения. Авторы и held не входят в независимый пересчёт. |
| `pulse_check.py` | Проверяет MD5 и побайтовое совпадение сохранённых отчётов с пересборкой в памяти; не проверяет истинность утверждений или отсутствие смысловой утечки будущего. |
| `src/astrafeed/adapters/http/app.py` | `/healthz`; `/pulse` и `/pulse/compare` регистрируются только при внедрении соответствующих функций. `format=json|md`, неизвестная тема 404, неправильное окно 422. Сам новостей не обрабатывает. |
| `tests/adapters/http/test_pulse.py` | Четыре теста HTTP-контракта на fake-провайдерах, не проверка реального корпуса/семантики. |

**Самостоятельного новостного слоя в этом Pulse нет.** Текст поста есть: `load_thread()` читает его, а `pulse_classify_thread.py` передаёт модели как контекст комментариев и опору на тему. Но пост не становится событием/авторской позицией в ответе, пост без комментариев не попадает в новостной раздел, происхождение/перепечатки не агрегируются. Подготовка включает сохранённые модельные ответы, агентские corrections и (для ZEC) группировку/формулировки. Новый topic нельзя обработать одним вызовом текущего `/pulse`.

Окно — календарные даты `YYYY-MM-DD..YYYY-MM-DD` включительно, фильтр `ts[:10]` по комментариям; это не контракт `1h/24h` с точными UTC-границами. Фильтруются ID, но заголовки единиц/наблюдения уже написаны по полному срезу. Модель также получала полный тред. Поэтому фильтрация не гарантирует отсутствие будущего влияния на смысл. Дополнительно `entity_candidates.py` строит статистику по всему корпусу.

Ещё два ограничения кода: подсчёт `authors` в агрегатах использует множество с `None` (неизвестные могут стать одним «автором»), тогда как `participants` отбрасывает пустые ключи; ключ группировки `thread_id/comment_id` не включает источник, возможна коллизия post_id разных каналов. В новой модели нужны составные ключи.

### Переиспользуемое в движке

- `textkey.py`, `prefilter/dedup.py`: нормализованный хеш текста и совпадение URL, память/опциональный repository. Сам `Deduper.filter` выбрасывает дубли и посты с общей ссылкой — для подсчёта распространения непригоден без изменения политики. Переиспользовать признаки, сохранять все публикации; общая ссылка в рекламе не доказывает дубль.
- `report/dedup.py`: `dedup_for_report`, `MergedItem`, точные дубли, все source links/member keys, earliest timestamp. Ближе к нужной обратимой группировке, но gist берётся у наиболее важного элемента, а не обязательно у первоисточника; текущие модели ориентированы на целый пост, не сегмент.
- `report/events.py`: без embeddings; кандидаты по времени, сущностям/действиям, доменам/URL, Jaccard, gist, `event_key=actor|action|object`; union-find, ограничения числа пар/размеров, затем LLM judge и детерминированная проверка согласованности. Ошибочные/неуверенные группы остаются отдельными пунктами. Recall сейчас только между разными каналами; общий домен может предложить пару, но не должен подтверждать событие. Связность цепочки и общие сущности недостаточно строги для гарантии нулевых ошибочных объединений из нового плана.
- `report/entities.py`: простой recall-детектор латинских Capitalized tokens, маленький словарь алиасов преимущественно AI-продуктов, denylist. Не готовая крипто-онтология и не доказательство предмета публикации.
- `adapters/llm/openrouter.py`, `contracts.py`: `OpenRouterLLMClient`, score через Instructor JSON mode + Pydantic response_model, ограничения батчей и повторов; `judge_events` со схемой результата. JSON mode/валидация — не доказательство фактической достоверности. Существующий score-контракт целого поста не заменяет новый контракт сегментов.
- `BudgetedClient`: резерв перед каждым completion, потолок токенов, отключённые SDK-retries, settlement по usage.cost; `SqliteSpendBudget`: глобальный дневной лимит в микродолларах с `BEGIN IMMEDIATE`. **Его нельзя подключать к замороженной astrafeed.db**: бюджету нужна отдельная writable БД. `AuditTransport` сохраняет разрешённые request/response с редактированием секретов, но это аудит, не готовый reuse-cache.

### Как `entity_candidates.py` находит темы

Это stdlib-детектор **кандидатов**, а не классификатор новостей. Читает весь read-only снимок: сначала посты, затем комментарии. NFKC/casefold, частичная нормализация омоглифов; URL/handles маскирует пробелами с сохранением offsets, адреса извлекает отдельно. Правила: cashtag, hashtag, CAPS, CamelCase, capitalized name, многословное имя, `Zcash (ZEC)`, имя после роли. Корпусная доля lowercase подавляет обычные слова; caps/title-case заголовки ограничивают слабые правила.

Повтор строки в ≥5 постах одного канала отмечается `template_candidate`; длинный одинаковый комментарий (≥100 символов) в ≥5 тредах тоже отмечается шаблонным. Упоминания не удаляются автоматически. TSV-реестр связывает алиасы; неоднозначные русские формы проверяются в контекстном окне ±60 символов, поддержка сама по себе не превращает ambiguous в confirmed. `entity_exclusions.tsv` исключает слабые правила в заданном контексте. Словарь из ≥2 постов помогает найти lowercase-названия в комментариях (длина ≥3, доля lowercase <0.5). `MIN_DOCS=2` ограничивает рейтинг, не хранение кандидатов. `phrase_head` сам по себе не считается упоминанием.

Выход: `candidates.json`, обзор Markdown, `detections.jsonl` с документом, точным surface, строкой/offset, фрагментом, правилом и статусом. Метка `confirmed` внутри детектора означает прохождение правил упоминания, не подтверждение сущности/события человеком. Подвал с котировками может дать упоминание ETH, но не новость об ETH. Контекст треда — пул для проверки, не автоматическое упоминание.

## Предложения — ещё не реализованы

Новый план делает новости самостоятельной обязательной частью Pulse; продуктовый документ пока описывает посты преимущественно как контекст. Это осознанное расширение поведения, заданное задачей, а не описание уже готового сервиса. Далее — проектирование разделов 1–5 и 8 нового плана.

### 1. Где разместить код

Для следующего исследовательского этапа рекомендую соседние stdlib-модули `docs/research/news_pulse_{load,classify,events,link,build,check}.py`, отдельный каталог `artifacts/news-pulse/<run_id>/` и единый manifest. Причина: текущий работающий Pulse и образцы живут здесь; можно сохранить их, быстро заморозить контракты и измерить качество без миграции ingestion. Чистые функции и явные аргументы БД/каталогов, без зависимости от глобального `REGISTRY` для выбора темы.

Переиспользовать чистые признаки движка через тонкий адаптер либо выделить их позже; не запускать весь старый brief pipeline, который удаляет публикации и использует другой score-контракт. В исследовании LLM-transport остаётся stdlib по образцу `pulse_classify_thread`; если нужен существующий Instructor/BudgetedClient, это уже отдельный адаптер из `src`, и такой режим честно требует окружение проекта. Не писать второй большой SDK. После проверки перенести модель в `domain`, координацию в `application`, read-only snapshot/file-cache/OpenRouter в `adapters`; HTTP оставить тонким. Сейчас перенос не является условием проверки гипотезы.

### 2. Платформенно-независимая модель

Разделить **Publication → Observation → Event/Thesis**, а реакции связать отдельными рёбрами.

- `Publication`: стабильный ID `(platform, source_external_id, message_external_id)`, source_id, nullable author_id, published_at, nullable discovered_at, edited_at/version/hash, url, original text, parent/thread IDs, platform-specific metadata отдельно. У старого снимка discovered_at=null, время импорта не подменяет историческое обнаружение.
- `Source` и `Actor`: площадка и человек/организация отдельно. Роль `official/editorial/author/participant/unknown` с основанием и временем действия записи. При отсутствии сведений — unknown; канал не становится автором. Известные авторы считаются по стабильным ключам, неизвестные строки считаются отдельно, без объединения в «одного неизвестного» и без попытки угадать личности.
- `Observation`: ID публикации + точный диапазон `[start,end)` и quote, entity references с spans, предмет/тезис, kind (`event_claim`, `author_position`, `reaction`, `promo`, `service`), actor/action/object и квалификаторы (версия, дата события, место, контрагент), nullable event_id/thesis_id. Один пост даёт несколько наблюдений.
- Происхождение отдельной осью: `original/retelling/repost/unknown`, nullable origin_publication/url, basis; проверка утверждения отдельной осью `unverified/source_statement/corroborated/disputed` со ссылками на основания. Самый ранний сохранённый пост не автоматически первоисточник. «Официальный источник» не равен независимой проверке всех его слов.
- `Relation`: from/to, тип `duplicate/retelling/position_on/reaction_to/reply_to`, evidence IDs/spans, метод, уверенность/воздержание, версия решения. Хранить все публикации и связи, не только representative.

### 3. Сегменты: правила плюс ограниченная LLM-классификация

Правила выделяют абзацы/ссылки/котировочные строки/повторяющиеся подвалы, предложения кандидатов тем, точные дубли. Не назначать всему посту одну метку; тикер в подвале остаётся локальным упоминанием и не переносит тему на остальные сегменты. Сохранять исключённые/сомнительные кандидаты для измерения полноты.

LLM через OpenRouter нужна для смешанных сегментов, actor/action/object, позиции автора и разрешения неоднозначного предмета; возвращает только структурированные наблюдения с точными spans и evidence IDs. Код проверяет диапазоны, quote==text[start:end], допустимые enum/ID, даты, полноту ответов, отсутствие неподтверждённых чисел/авторства. При ошибке — held/unclear с причиной, не выдуманный результат; арифметика только в коде. Сами исходные сообщения трактовать как данные, не инструкции модели. Классификацию группировать в ограниченные батчи; точные копии могут разделять содержательную классификацию, сохраняя собственные метаданные.

Использовать существующий паттерн `request.json`, `response.json`, `meta.json`, `labels.json`, `PULSE_REUSE`. Уже сейчас reuse проверяет hash prompt/input, модель и pinned provider, а grounding хранится отдельно от исходного запроса. Для новостей дополнить идентичность кэша схемой, версиями детектора/алиасов/правил, временным cutoff, составом evidence и DB fingerprint. Сырые ответы неизменяемы, коррекции — отдельным слоем. Reuse при несовпадении завершается ошибкой без автоматического сетевого fallback. Повторяемость обеспечивается сохранённым ответом, не одной temperature=0.

Новые LLM-вызовы возможны только в отдельно разрешённом этапе; в задаче A их нет. Для будущего online-режима — явный opt-in, ограничение числа вызовов/токенов и бюджет с резервированием в отдельном хранилище, включая повторы. Offline-путь и HTTP не читают ключи и не обращаются к сети.

### 4. События и распространение без embeddings

Точные дубли: нормализованный хеш содержательного сегмента при сохранении исходных spans и всех членов. Близкие пересказы: candidate pairs по нормализованной предметной URL, actor/action/object, квалификаторам и ограниченному времени; дешёвое текстовое сходство лишь предлагает пару. Не объединять по тикеру, общему домену или рекламной ссылке. Самостоятельные оценки связывать с событием как позиции, не считать перепечатками.

Одинаковый актор/действие без совпадения объекта/версии/даты недостаточен. Явные противоречия дают запрет merge; оставшиеся трудные пары можно передавать cached LLM judge. Для итоговой группы проверять совместимость предмета всех членов, чтобы транзитивная цепочка A–B–C не склеила A и C без основания. Неуверенные пары оставлять отдельными, фиксировать abstention; одинаковые события одного канала тоже должны обрабатываться (в отличие от старого cross-channel recall).

Группа = одно событие; отдельно считать distinct publications, channels, known authors, неизвестное авторство, origins, reprints, unknown provenance. Суммы групп не обязательно равны числу уникальных постов: один пост может описывать два события. Не называть распространение независимыми подтверждениями. Дедуп в этом слое обратимый; повторяющиеся котировки не становятся событием, общий источник пересказа сохраняется.

### 5. Обсуждения, окно и ответ

Сначала генерировать кандидатов связи по parent/reply chain, явной ссылке или цитате; затем проверять **предмет конкретной реплики** и сегмент поста. Родство с постом не доказывает реакцию на каждую его новость. Тип цели: конкретное событие, авторский тезис, проект в целом, другой предмет; сомнение → topic-level/unlinked с причиной. Жалоба на NFT-сайт в экосистеме ZEC относится к сайту, а не автоматически к сети ZEC. Для каждого ребра — основание, доступная цепочка и точные spans.

Нормализовать окно в UTC `[start,end)`, date-only legacy-запрос трактовать как дни включительно через следующий UTC midnight. До детекции, статистики шаблонов, LLM, группировки и рендера отсечь публикации/комментарии за cutoff. Для сравнения A и B строить независимые представления; нельзя строить глобальную группу по A+B и затем просто прятать ссылки B. Кэш также привязан к cutoff. Контекст до начала окна допустим как явно отделённая предыстория, не учитывается в числах текущих публикаций; контекст после конца запрещён.

Два режима времени: `publication_replay` по сохранённому времени публикаций с честным предупреждением об отсутствии времени обнаружения/истории редакций; строгий `as_known_at` потребует discovered_at и версий исходников. Сейчас его достоверно восстановить нельзя. Факты о «раньше новостей» и «впервые системой» из такого снимка не заявлять. Даже время события, названное в тексте, не заменяет published_at.

Единый `build(topic, window, snapshot, cache)` возвращает JSON и из него Markdown: `events`, `distribution_and_positions`, `discussion`, `changes`, плюс coverage/limitations/evidence и до пяти содержательных observations. Новость без комментариев полноценна: «в собранных обсуждениях реакция не найдена». Нет новостей, есть обсуждение — полезный discussion-only ответ. Нет модельной классификации — partial/not_processed, не «новостей нет». Изменения включают новые события/позиции и объём обсуждений, отдельно смену охвата каналов, ошибки сбора, неизвестное авторство, длину периодов.

### 8. Сквозной запуск и критерий окончания

Предлагаемый интерфейс (команды **ещё не существуют**):

```sh
PULSE_REUSE=1 make news-pulse-demo PULSE_DB=astrafeed.db TOPIC=zec WINDOW=2026-09-17..2026-09-19
# проверка fingerprint → read-only выборка → cached classify → groups/links → JSON+MD → HTTP
curl 'http://127.0.0.1:8000/pulse?topic=zec&window=2026-09-17..2026-09-19'
curl 'http://127.0.0.1:8000/pulse?topic=zec&window=2026-09-17..2026-09-19&format=md'
```

CLI и внедряемый `/pulse` используют один build и один manifest; разница только в записи файлов CLI и HTTP-представлении. Чтение новых публикаций не ограничено списком подготовленных тредов; новая тема выбирается автоматически из корпуса. Для неготового кэша возвращать явную неполноту, а разрешённый отдельный prepare-запуск классифицирует недостающее. При запуске фиксировать версии, покрытие, cutoff, hashes request/response и DB MD5; `check` проверяет воспроизводимость, ссылки, независимый пересчёт и отсутствие будущих evidence.

До настройки зафиксировать проверочную выборку из раздела 6: ≥40 постов, ≥20 комментариев, ≥2 темы, ≥3 канала, ≥20 пар (10 одинаковых/10 разных событий), включая трудные пары одного токена и границы времени. Агентскую разметку так и назвать; tuning держать отдельно. Проверить перенос на ранее не использованную тему/период без ручной правки группировок и текста.

Готовность не доказана текущим `pulse_check`: нужны отдельные числители/знаменатели и ошибки по всем метрикам плана: precision отбора ≥95%, recall ≥90%, false merge=0 на отрицательных парах, same-event recall ≥90%, точность заявленных discussion-links ≥90% с числом воздержаний, grounding утверждений ≥95%, выдуманные цены/даты/авторство/официальность=0, future leakage=0, числа=100% при независимом пересчёте. Непредставленные категории помечать непроверенными. До этого слой остаётся экспериментальным, даже если API и один запуск работают.

Основные риски: будущие сообщения влияют на словарь/классификацию/группы; отсутствует история обнаружения и редакций; котировочный подвал создаёт ложную релевантность; перепосты выглядят независимыми источниками; коллизии Telegram ID; неизвестные авторы и неполный контекст; перекос корпуса в один агрегатор. Предложенные ключи, provenance, локальные spans, cutoff до обработки и раздельный coverage предназначены закрыть именно эти риски.
