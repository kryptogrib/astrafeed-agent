# Предмет реакции в ветке: связыватель против контекстного LLM-разбора

Исследовательский эксперимент. Отвечает на вопрос: на что реагирует комментарий — на событие поста, на тезис автора, на проект в целом или на другую тему? Цель — точнее отвечать «что комьюнити думает и почему». Production-путь не менялся. Все файлы эксперимента лежат отдельно:

- `docs/research/reaction_subject.py`
- `docs/research/reaction_subject_labels.py`
- `artifacts/reaction-subject/`
- `tests/research/test_reaction_subject.py`
- v2: `docs/research/reaction_subject_v2.py`, `artifacts/reaction-subject/v2/`, `tests/research/test_reaction_subject_v2.py`

## Как устроено

1. **Выборка** (`sample`). Использованы прогоны eth/zec/arc/aave за окно 2026-09-09..2026-09-23 на той же БД (md5 8618…).
   - Отобраны 31 ветка и 111 комментариев из discussion.
   - Посты из frozen gold (news-eval, news-tune) исключены.
   - Если ветка встречается в нескольких темах, она берётся один раз. Из каждой ветки — не больше 6 реплик, выбор по хешу.
   - Тип ветки определяется по выходу пайплайна:
     - news — есть события;
     - author_forecast — есть тезисы автора;
     - mixed — есть и то и другое;
     - topic_shift — нет ни того, ни другого.
   - Разбиение по хешу ветки внутри типа: dev 9 веток / test 22. Если тип представлен одной веткой, она уходит в test.
2. **Разметка** (`label`). Предварительная, её делал агент; она **закреплена в 75942e3 до написания промпта**.
   - Метки: event / author_thesis / project / other_subject / unclear, плюс skip для пустого текста.
   - 32 спорных случая отмечены `disputed` и требуют человеческой проверки.
   - Реплика из test, почти повторяющая dev, не оценивается (таких 3).
   - В test оцениваются 69 реплик: event 13, author_thesis 7, project 2, other_subject 29, unclear 18.
3. **Ветки сравнения** (`llm`, `eval`):
   - `baseline` — текущий `link_comment` без изменений. `topic_level` считается воздержанием (unclear).
   - `context` — один вызов на ветку. Модель видит пост, события и тезисы этого поста, реплики и цепочку **только предшествующих** ответов. Других веток модель не видит. **Исправление после ревью:** будущие реплики модель видела. В одном запросе были все выбранные реплики ветки, поэтому ранняя реплика видела более поздние соседние: в test это 47 из 69 оцениваемых. Тест проверял только цепочку, не весь запрос. Кроме того, заголовок события брался из общей группы и мог прийти из другого поста или дня. Результаты v1 ниже — не чистое измерение; см. раздел «v2».
     - Выход по каждой реплике: target, target_id, точный фрагмент реплики и точный фрагмент контекста.
     - Если фрагмент неточный или target_id чужой, связь понижается до unclear и помечается (`invalid_basis`).
   - `context+verify` — второй вызов на каждую ветку, где есть предложенные event-связи. Проверяющий ищет причины отклонить связь. Отклонённая связь становится unclear, но реплика остаётся в обсуждении темы.
   - `+id` — действующий production-контракт из 34a6222: event-связь должна назвать событие этого прогона. Event без target_id считается unclear. Контракт применён после того, как я увидел ответы. Это не новое правило, подобранное по test, но оговорку фиксирую.
4. Промпт v1 написан один раз. Итераций по dev не было: dev и test оба фактически отложены.
5. Запросы, ответы, meta и usage лежат в `artifacts/reaction-subject/cache/`. Повторный запуск без `--pay` — это 44 cache hit и 0 вызовов.

### Что изменилось по существу (baseline → context+verify+id)

Все пункты ниже — примеры из test.

- **Ложные приписывания устранены (3).** Baseline отнёс к «проекту» два поста-пересказа: машинный перевод дайджеста и перепост новостей NEAR. Реплику «АКА отлично покормили, а вот Arclings походу заскамили» baseline отнёс к другой теме. Теперь первые два — «другая тема», третья — воздержание, потому что фрагмент контекста неточный.
- **Правильные связи сохранены.** У baseline верных заявленных связей не было, сохранять нечего.
- **Новые правильные связи (33).** Среди них:
  - «xaut давно же был на v4» и «Золото? Вот это поворот!» → приём золота в залог Aave;
  - «Ну зашквар или новый уровень?» → запуск Arc от Circle;
  - «ващета сегодня» → дата мейннета Arc;
  - «дальше 1500)» и «До 3к эфир подарочно выглядит» → прогноз автора «дальше 3к»;
  - «ага, Раванга это и предположила» → вывод автора об украденном ключе.
- **Новые ошибочные связи (15).** 9 реплик без предмета уверенно названы «другой темой» или «проектом»; одна реплика о другой теме названа проектом; остальное — потерянные реакции ниже.
- **Потерянные реакции.** Реплика, у которой в эталоне есть предмет, уходит из темы в «другую тему»:
  - «То бишь hype или zec 😁» — уточнение совета автора;
  - «Рекомендую посмотреть пару usdjpy к btcusdt и ethusdt…» — развитие тезиса автора;
  - «я стал откупать эфир и щитки…» — об ETH в целом;
  - «а разрабы?» — о команде Arc.

  Эти четыре реакции пропадут из ответа по теме. Ещё «готовы ректоваться?» ушла из события в проект, а «На койнгеко написали что ключ украли» стала воздержанием: событие указано неверно.
- **Отсечено проверяющим (9).**
  - пять реплик «не жирно ли работягам» модель привязала к конкурсу Extended — эталон неопределённый, спорный;
  - «согласен» — это согласие с оценкой автора, а не событие;
  - реклама депозитов fomo;
  - одна верная реакция («Вот это поворот, золото в крипте, интересно») — потеря;
  - «На койнгеко…».
- **Отсечено контрактом id.** Реплики про другие пункты дайджеста (Yield Fields, коррекция BTC) модель назвала event без id; контракт перевёл их в воздержание. На dev это же случилось с Linera, ArcHub и NFT-минтом: 10 из 11 ложных event были без id. Это расхождение словаря: модель считает событием любой факт поста, а продукту нужно событие темы.

## Ограничения

- **Разметка предварительная, одного агента.** 32 из 111 реплик спорные; на бесспорных выводы те же. Автор разметки писал и промпт. Тексты test-веток он видел при разметке, но промпт не подбирался по ответам на test.

## v2: изолированный контекст и строгая проверка

После ревью v1 найдены три дефекта:

- **Утечка будущего.** Все реплики ветки шли одним запросом.
- **Пропущенный вердикт проверки считался сохранением связи.**
- **Заголовок события приходил из другого поста.** Он брался из общей группы события: 3 случая, в том числе «завтра» от 15.09 под постом 16.09.

v2 (`reaction_subject_v2.py`) исправляет их на **той же** выборке и тех же метках. Поэтому это регрессионное сравнение с v1, а не новая независимая проверка. v1 и его кеш не менялись; v2 пишет в `artifacts/reaction-subject/v2/`.

**Что изменилось в v2:**

- Один запрос на реплику. В запросе: `requested_topic`, пост, события только цитатами из этого поста (без групповых заголовков), тезисы этого поста, сама реплика и её цепочка предков.
- Проверка утечек выполняется на реально отправляемом payload: лишние поля, более поздняя цепочка или пост, текст более поздней реплики ветки. На всех 102 запросах — 0 нарушений.
- Тема запроса передаётся явно. Раньше она была только в id, хотя от неё зависят project и other_subject.
- Контракт id применяется до проверки и к событиям, и к тезисам. Связь без id события или тезиса этого поста остаётся на уровне темы (`no_id`). На проверку идут только связи с id события.
- Проверка засчитывает только явный `keep` с точным фрагментом реплики или цепочки. Пропуск, неизвестный вердикт или фрагмент не из текста — это `unverified`.
- Невалидный ответ первого прохода — это `invalid`: неизвестный target, фрагмент не из текста, чужой id. Оба статуса считаются «необработанными» — отдельно от содержательного unclear и от cache miss.
- v1 для сравнения пересчитан по тем же строгим правилам. Метрики v1 совпали с отчётом выше: в сохранённых ответах v1 пропусков вердикта не было.

Без проверки v2 делает меньше ошибок: 22 против 28, ложных event 5 против 13, при той же полноте 0.71.
   - На dev эффект сильнее: v1 context — 11 верных из 28, v2 context — 22 из 28. Но промпт писался по dev, поэтому dev — не оценка.

2. **Проверяющий проход в v2 строже.** Он отклонил 3 верные event-реакции («xaut давно же был на v4», «Ну зашквар или новый уровень?», «Вот это поворот, интригующе же») а также одну реакцию на тезис, которую первый проход ошибочно назвал событием. Взамен добавилась одна верная связь. Для event цена «0 ложных» — полнота 8/13 вместо 11/13 без проверки.
3. **«Необработанное» — новый видимый класс.** 3 реплики test: модель вернула пустой `comment_fragment` для other_subject (приветствие бота, копия поста) или фрагмент с отличием в символах. Раньше такие ответы v1 тихо превращал в unclear.
4. **project и other_subject по-прежнему нельзя использовать** для удаления реакций из ответа: 11 ошибок встречаются в обеих версиях, и большинство из них — other_subject на эталонных unclear.
5. **Стоимость:** 122 вызова (102 первого прохода + 20 проверок), $0.0118, 410 с последовательно. Это примерно в 1.4 раза дороже v1 ($0.0085, 44 вызова): теперь пост повторяется в каждом запросе. Экстраполяция на 183 ветки БД — около $0.07. Остаток лимита пользователя $1 после v1 и v2 — около $0.98.

**Ограничения v2:**

- **Текст поста.** Используется сохранённая версия поста. Если пост редактировали, это не доказывает, что комментатор видел именно этот текст.
- **Метки предварительные**, одного агента. «8/8 event» — регрессионный результат на уже просмотренной выборке, а не независимая приёмка продукта.
- **Выборка та же, что в v1.** Test уже просмотрен при разметке и после v1, поэтому holdout-ом для дальнейшей настройки он не считается.

Выводы:

- **Ложных event-связей 0, как и на старом test.** Но из 5 доступных связей подтверждена 1. Верификатор отклонил 2 верные связи с e9 («Arc что-то готовят для своих архитекторов»): шутки о том, что именно приготовят. Это тот же компромисс строгой проверки, что и 8/13 против 11/13 на старом test.
- **Полноту ограничивает извлечение.** 25 из 30 реакций на событие или тезис не имеют цели с id, поэтому по контракту их нельзя связать. Это потолок достижимой полноты, а не доказательство, что извлечение исправит эти 25 случаев. Связыватель на них не проверялся. Реплики, которые спорят с тезисом автора (например, «$ETH looks like shit»), модель относит к project или other_subject. Для панели это верхний уровень, реакция не теряется.
- **5 примеров не обработаны** (invalid, `comment_fragment` не найден в комментарии). Все 5 — не event.
- **Разметка ненадёжна.** Спорные метки согласуются с моделью на 8 из 30 заявленных против 44 из 53 у бесспорных. Разметку этих 43 должен проверить человек, прежде чем цифры по ним что-то значат.
- **Сбой сборки данных.** Флаг `context_incomplete` в адаптере отражает media-only комментарии, а не оборванные цепочки. Это вынесено в [follow-up](context-incomplete-followup.md); эксперимент использует флаги на уровне примера.

**Предлагаемый следующий шаг — извлечение тезисов автора.** Для постов с обсуждением выделять 0–3 тезиса автора: id, дословная цитата из поста, проверка, что цитата есть в тексте. Затем повторить этот же прогон на кэше. Без этого шага метка thesis не может получить id ни в одном примере. Сколько связей появится после извлечения, покажет только повторный прогон. Объединение событий и отбор новостей — после.

## Рекомендация

**Массово пока не внедрять.** Следующий шаг — конфигурация v2 context+id+verify, только для связей с событием или тезисом, у которых есть id. Всё остальное остаётся на уровне темы.

- На test она не дала ни одной ложной event-связи. Найдено 8 из 13 реакций на событие и 3 из 3 проверяемых реакций на выделенный тезис. Цена — копейки.
- Решения «project» и «other_subject» из модели в продукт не переносить: реплики остаются на уровне темы, иначе реакции пропадают из ответа.
- Главный источник пропусков по тезисам: пайплайн не выделяет тезис с id и цитатой. Следующий небольшой шаг — извлечение тезисов автора с id и цитатой для постов с обсуждением.

Перед решением о внедрении:

1. Человек проверяет 32 спорные метки.
2. Test из новых каналов собран (раздел «Перенос на новые каналы»). Смешанных и тезисных веток в нём 0, пока не извлекаются тезисы.
3. Решить, какая цена проверки допустима: 0 ложных event при 8/13 или 4 ложных при 11/13.

Объединение событий, инфраструктура и продуктовые пороги не затрагивались.
